# 0007 — Use a Stable Execution Prompt for Ready Milestones

## Status

Accepted; revised in guide system v0.7.0 and clarified in v0.7.3.

## Context

Disconnected planning and implementation interfaces must not depend on shared chat state. Earlier guidance required each planning task to generate a bespoke execution prompt.

With the two-phase milestone lifecycle, the durable handoff is the ready milestone plus the project authority it references. Regenerating a per-milestone execution prompt duplicates methodology, can drift from the canonical execution contract, and can repeat large amounts of milestone or authority content that the executor will already read.

Long implementation runs additionally need persistent execution state, but that state belongs to the implementation phase and must not be confused with a second planning contract.

## Decision

Use `templates/prompts/execute-milestone.md` as the stable execution prompt for ready milestones.

Planning must produce a self-contained ready milestone. A planning interface may emit a short handoff note identifying the primary milestone path and any transport/application instructions, but it must not regenerate the execution methodology.

Do not create per-milestone `EXECUTE-Mxxx.md` or equivalent files that duplicate the canonical execution prompt, repeat milestone acceptance criteria, or restate project authority merely for implementation handoff.

When an overlay or other transport package requires application instructions, those instructions may exist as a small transport artifact. They should explain how to apply the package and identify the primary ready milestone; they are not execution methodology or project authority.

The implementation phase must be able to proceed from:

1. the canonical execution prompt;
2. the ready milestone;
3. the localized project authority referenced by the milestone;
4. the live repository;
5. optional transport/application instructions needed to reach that repository state.

The executor may create repository-local operational state such as the v0.7.3 execution ledger. That state is derived from the ready milestone during implementation and does not replace or amend planning authority.

## Consequences

- the ready milestone is the durable planning-to-implementation semantic handoff;
- execution methodology has one canonical prompt instead of per-milestone copies;
- disconnected Chat/Codex or other interface boundaries remain supported;
- planning conversation history is not implementation authority;
- concise overlay/application instructions remain valid transport context;
- implementation progress state is executor-owned rather than generated by planning;
- large duplicated execution handoff prompts should not be produced for new milestones.
