# Migration — Guide System 1.0.0 → 1.0.1

**Classification:** Patch clarification of decision-complete implementation readiness, verification feasibility and correction discipline. No mandatory product-repository restructuring or retrospective rework of completed milestones.

1. After `v1.0.1` is published, update the **complete unmodified** repository-local `.guide/system/` snapshot from that tag and in the same change set `.guide-profile.json`'s `guideSystem.version`, `tag`, `revision` (peeled commit SHA), and any applied shared profile versions. Preserve local-profile versions and normal project authority.
2. For **new substantive milestones**, investigate the intended executor's actual tools/OS/runtime, permissions, and accessible execution locations sufficiently to make implementation and focused milestone verification credible. Distinguish verified access from documented or assumed capabilities, and critically review the draft before `ready`. Discover and resolve quality-critical design and verification decisions or bound their evaluation; translate applicable project authority into concrete requirements, design nontrivial verification with discriminating conditions and independent oracles, and review both target-state feasibility and conformance.
3. For **already ready but not completed** milestones, revisit readiness only when there is a material reason to suspect a missing quality-critical decision, insufficient obligation coverage, or implementation or milestone verification cannot run as planned (for example, missing SDK/runtime, unavailable CI/desktop session, or unauthorized integration target). Reconcile material changes with planning. Do not automatically rewrite every active milestone or its ledger.
4. For newly confirmed planning or earlier-review oversights, the review workflow may start a project-local `docs/agent-feedback/planner.log` with one concise entry per miss. Do not create an empty file or backfill completed milestones; the log is for retrospective learning, not a readiness or acceptance gate.
5. Preserve the planner-seeded obligation ledger for substantive milestones, stable acceptance identities, bounded implementation experimentation, and release-qualification policy. For substantive corrections requiring material contract or inventory changes, use the authorized versioned milestone amendment and reconcile the existing ledger, preserving original identity and history. No new ledger type or mandatory seed is introduced. No new environment inventory, evidence cases, validation receipts, or per-obligation test mappings.

A straightforward snapshot/metadata upgrade may be made directly under the guide update workflow. This patch does not require a migration milestone solely for changing the guide pin.
